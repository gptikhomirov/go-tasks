## 🔴 Настоящие баги (приоритет)

### 1. `methodHandler` не делает `return` после ошибки
`cmd/api/main.go:57-65`

После `http.Error(...)` функция не прерывается и всё равно вызывает `handlerFunc(w, r)` —
в ответ пишется и 405, и тело настоящего хендлера.

**Фикс:** добавить `return` после `http.Error`.
Общее правило: после записи ответа в хендлере — всегда `return`.

### 2. `GetAll` не возвращает `id` и `updated_at`
`internal/database/tasks.go:23-27`

`SELECT title, description, completed, created_at` — нет `id`, поэтому в JSON у всех
задач `"id": 0`. Клиент не сможет обратиться к задаче.

**Причина глубже — модель БД ≠ модель ответа.** Сейчас `models.Task` используется
сразу для двух вещей: чтения из БД и сериализации в JSON-ответ. Поэтому любое поле
структуры (`ID` с тегом `json:"id"`) всегда попадает в ответ, а у `int` нулевое
значение — `0`, и «просто не показывать» его нельзя. Это называется «протекание»
БД-модели в HTTP-слой: представление данных наружу завязано на то, как они лежат
в базе.

**Фикс.** Варианты:

- `omitempty` (`json:"id,omitempty"`) — быстро, но криво: поле прячется по значению
  (`0`), а не по смыслу. На `GET /tasks/{id}` id нужен и покажется, а если реальный
  id окажется 0 — пропадёт. Логика «показывать/нет» завязалась на значение.
- `json:"-"` — никогда не сериализовать, но из БД читать можно. Не подходит, если
  id нужен хотя бы на одном эндпоинте (`GET /tasks/{id}`).
- **Рекомендуется:** отдельная структура ответа (DTO) только с нужными полями:
  ```go
  type TaskListItem struct {
      Title       string    `json:"title"`
      Description string    `json:"description"`
      Completed   bool      `json:"completed"`
      CreatedAt   time.Time `json:"created_at"`
  }
  ```
  `sqlx` сканирует `SELECT title, description, completed, created_at` прямо в неё.
  `id` исчезает не потому что «спрятан ноль», а потому что поля физически нет —
  БД-модель больше не протекает в HTTP. Стандартный для Go приём: разные структуры
  под БД и под API; список задач и одна задача — разные представления.

Либо, если такая детализация ответа пока не нужна, — просто добавить `id, updated_at`
в SELECT (тогда возвращается полный `models.Task`).

### 3. Проверка «не найдено» при обновлении никогда не срабатывает
`internal/handlers/handlers.go:110` + `internal/database/tasks.go:49`

БД возвращает текст `task with id %d not found`, а хендлер ищет `record not found` —
строки не совпадают, поэтому update несуществующей задачи даёт **500 вместо 404**.
Та же логическая проблема в `GetTask` (отдаёт 400 вместо 404).

**Фикс (идиоматично):** sentinel-ошибка + `errors.Is` вместо сравнения текста.
```go
// database
var ErrTaskNotFound = errors.New("task not found")
return nil, fmt.Errorf("task with id %d: %w", id, ErrTaskNotFound)
// handler
if errors.Is(err, database.ErrTaskNotFound) { ... 404 ... }
```

### 4. `Update` возвращает не то, что вернула БД
`internal/database/tasks.go:100-106`

Скан идёт в `updatedTask`, а возвращается старый `task`.

**Фикс:** `return &updatedTask, nil`.

## 🟡 Идиоматичность

### 5. Роутинг можно упростить (Go 1.22+, в проекте Go 1.26)
`http.ServeMux` умеет метод + параметры пути. Убираются `methodHandler`,
`taskIDHandler`, `getIdFromUrl`:
```go
mux.HandleFunc("GET /tasks", handler.GetAllTasks)
mux.HandleFunc("POST /tasks", handler.CreateTask)
mux.HandleFunc("GET /tasks/{id}", handler.GetTask)
mux.HandleFunc("PUT /tasks/{id}", handler.UpdateTask)
mux.HandleFunc("DELETE /tasks/{id}", handler.DeleteTask)
// id, err := strconv.Atoi(r.PathValue("id"))
```
Заодно уходит не-RESTful `/tasks/create` (создание — это `POST /tasks`).

### 6. `err == sql.ErrNoRows` → `errors.Is(err, sql.ErrNoRows)`
`internal/database/tasks.go:48` — `==` ломается на обёрнутых ошибках.

### 7. `panic` в HTTP-хендлере
`internal/handlers/handlers.go:25-27` — ошибку кодирования JSON лучше логировать,
а не паниковать (`log.Printf("encode response: %v", err)`).
