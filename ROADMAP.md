# ROADMAP

Учебный маршрут REST API на Go — **с абсолютного нуля** (первая ручка,
возвращающая строку) до полноценного сервиса со списками, фильтрами,
миграциями и связанными сущностями.

Цель проекта — научиться писать **Go-код + SQL + REST API**, понимая *почему*
так, а не только *как*. Шаги идут **строго по возрастанию сложности**. Каждый —
целостная итерация: после него проект компилируется и работает. Можно пройти
весь путь с шага 1, используя этот файл как учебник и чеклист.

Каждый шаг описан единообразно:
- **Что это и зачем** — для того, кто впервые слышит термин.
- **Какие бывают** — варианты с плюсами/минусами и где они применяются (если есть выбор).
- **Что реализуем** — конкретные действия этого шага.
- **Файлы** — какие файлы/папки создаются (`+`) или меняются (`~`) на этом шаге.
- **Где какой слой** — как задача раскладывается по `handlers → database → models`.
- **Как проверить** — сценарии, которыми убеждаешься, что работает.

Маркеры сложности: 🟢 низкая · 🟡 средняя · 🟠 высокая.

**Итоговая структура проекта** (к концу маршрута):
```
go-rest/
├── cmd/api/main.go          точка входа: env, сборка зависимостей, роутинг
├── internal/
│   ├── handlers/            HTTP-слой (обработчики, хелперы, middleware)
│   ├── database/            доступ к данным (сторы, SQL)
│   └── models/              структуры данных (сущности, DTO)
├── migrations/              SQL-миграции (goose)
├── docker-compose.yml       Postgres для разработки
├── go.mod / go.sum          зависимости
└── ROADMAP.md
```
Ниже видно, на каком шаге появляется каждый кусок.

## Фаза A — HTTP + база с нуля

> База подключается одним из первых шагов; CRUD пишется сразу на SQL,
> без выбрасываемого in-memory этапа. Первые два шага — знакомство с
> `net/http` без БД.

### 🟢 Шаг 1. Hello-сервер

**Что это и зачем.**
HTTP-сервер — это программа, которая слушает порт и на каждый входящий запрос
отдаёт ответ. В Go для этого есть стандартная библиотека `net/http` — ничего
ставить не нужно. Минимальный сервер: «зарегистрировать обработчик на путь» +
«начать слушать порт».

**Что реализуем.**
- Инициализировать модуль: `go mod init go-rest`.
- В `main.go` зарегистрировать обработчик на `GET /` (`http.HandleFunc`).
- Запустить сервер на порту 8080 (`http.ListenAndServe(":8080", nil)`).
- Обработчик пишет в ответ обычную строку (например, `"ok"`).
- Понять три базовых объекта: `http.Handler` (что обрабатывает),
  `http.ResponseWriter` (куда писать ответ), `*http.Request` (что пришло).

**Файлы.**
```
+ go.mod
+ cmd/api/main.go
```

**Как проверить.**
```
curl localhost:8080      → ok
```

### 🟢 Шаг 2. JSON вместо строки

**Что это и зачем.**
REST API общается не текстом, а **структурированными данными** — почти всегда
JSON. В Go объект превращается в JSON через `encoding/json` (этот процесс
называется *маршалинг*/*сериализация*). Клиент по заголовку `Content-Type`
понимает, что пришёл JSON, а не текст.

**Что реализуем.**
- Та же ручка, но отдаёт JSON: `json.NewEncoder(w).Encode(someStruct)`.
- Выставить заголовок `Content-Type: application/json`.
- Прочувствовать разницу: текст «ok» vs объект `{"status":"ok"}`.

**Файлы.**
```
~ cmd/api/main.go
```

**Как проверить.**
```
curl -i localhost:8080   → в заголовках Content-Type: application/json, тело — JSON
```

### 🟡 Шаг 3. Postgres в docker-compose

**Что это и зачем.**
Данные должны где-то жить между перезапусками сервера — в базе данных.
PostgreSQL — реляционная СУБД, индустриальный стандарт. Чтобы не ставить её
в систему руками, поднимаем в Docker: один файл `docker-compose.yml` описывает
контейнер с БД, и она поднимается одной командой, одинаково на любой машине.

**Что реализуем.**
- `docker-compose.yml` с сервисом `postgres`: образ, логин/пароль/имя БД через
  переменные окружения, проброс порта 5432, volume для хранения данных,
  healthcheck.
- `sql/init.sql` — схема таблицы `tasks` + несколько сид-записей. Postgres
  выполняет файлы из `/docker-entrypoint-initdb.d/` **при первом** создании БД.
- Поднять: `docker compose up -d`.

**Важно понять про volume.**
Данные лежат в volume, который **переживает контейнер**. `init.sql` выполняется
только при первой инициализации пустого volume. Значит смена схемы = либо новая
миграция (фаза C), либо `docker compose down -v` (удалить volume) и поднять
заново — **с потерей данных**. Это типичная ловушка новичка.

**Файлы.**
```
+ docker-compose.yml
+ sql/init.sql
```

**Как проверить.**
```
docker compose ps                          → контейнер healthy
docker compose exec postgres psql -U <user> -d <db> -c "SELECT * FROM tasks;"
```

### 🟡 Шаг 4. Слой database

**Что это и зачем.**
Go-программа сама не умеет говорить с Postgres — нужен **драйвер**
(`lib/pq` или современный `pgx`). Поверх драйвера удобно положить тонкую
обёртку `sqlx` — она умеет раскладывать строки результата по полям структуры
(по тегам `db:"..."`), избавляя от ручного перечисления колонок. Сырой SQL при
этом остаётся — никакого ORM.

**Что реализуем.**
- Подключить `sqlx` + драйвер (`go get`).
- Функция `Connect()`: открыть соединение по строке подключения, настроить пул
  (`SetMaxOpenConns`, `SetMaxIdleConns`), сделать `Ping` для проверки.
- Строку подключения (`DATABASE_URL`) читать из переменной окружения, не хардкодить.
- В `main.go` — вызвать `Connect()` при старте.

**Что понять про пул соединений.**
Открывать новое соединение к БД на каждый запрос — дорого. Пул держит набор
открытых соединений и переиспользует их. `MaxOpenConns` ограничивает нагрузку
на БД (иначе сотни параллельных запросов положат Postgres).

**Файлы.**
```
+ internal/database/database.go   (Connect, настройка пула)
~ cmd/api/main.go                 (читает DATABASE_URL, вызывает Connect)
~ go.mod / go.sum                 (sqlx + драйвер)
```

**Как проверить.**
- Сервер при старте логирует успешное подключение; при неверном `DATABASE_URL`
  падает с понятной ошибкой.

### 🟡 Шаг 5. GET /tasks из базы

**Что это и зачем.**
Первый «сквозной» путь данных: HTTP-запрос → обработчик → запрос в БД → ответ
JSON. После этого шага у тебя есть скелет настоящего REST-эндпоинта.

**Что реализуем.**
- Модель `Task` в `models` — поля с тегами `json` (как называется в API) и
  `db` (как называется колонка в БД).
- `TaskStore.GetAll()` — выполняет `SELECT ... FROM tasks`, возвращает `[]Task`.
- Обработчик `GET /tasks` — зовёт стор, отдаёт массив JSON.
- Роутинг — через `http.ServeMux` с method-aware паттернами (Go 1.22+):
  `"GET /tasks"`. Сторонний роутер не нужен.

> На шагах 5–9 обработчики живут прямо в `cmd/api/main.go` — так проще начать.
> На шаге 10 их вынесем в отдельный слой (это намеренное упражнение по рефакторингу).

**Подсказка про пустой список.**
`var tasks []Task` при отсутствии строк остаётся `nil` и сериализуется в `null`.
Чтобы API возвращал `[]`, инициализируй пустым слайсом: `tasks := []Task{}`.
Это контракт: «список» всегда массив, не `null`.

**Файлы.**
```
+ internal/models/task.go         (Task)
+ internal/database/tasks.go      (TaskStore, GetAll)
~ cmd/api/main.go                 (роут GET /tasks + обработчик)
```

**Как проверить.**
```
curl localhost:8080/tasks   → JSON-массив сид-задач
```

### 🟡 Шаг 6. GET /tasks/{id} + сигнальные ошибки

**Что это и зачем.**
Получение одной записи по идентификатору. Здесь впервые встаёт вопрос:
*что вернуть, если записи нет?* Правильный ответ — `404 Not Found`, а не пустой
объект и не `500`. Чтобы handler понял, что именно «не найдено», слой database
сообщает об этом **сигнальной (sentinel) ошибкой**.

**Что это за паттерн.**
В пакете `database` объявляется `var ErrTaskNotFound = errors.New(...)`. Когда
запись не найдена, стор оборачивает её: `fmt.Errorf("...: %w", ErrTaskNotFound)`
(`%w` сохраняет «цепочку»). Handler проверяет `errors.Is(err, ErrTaskNotFound)`
→ отдаёт 404; любая другая ошибка → 500. Так слой БД не знает про HTTP-статусы,
а handler не знает про SQL — каждый отвечает за своё.

**Что реализуем.**
- `id` из пути через `r.PathValue("id")`, распарсить в число (мусор → `400`).
- `TaskStore.GetByID(id)` — `SELECT ... WHERE id = $1`; если строк нет, вернуть
  `ErrTaskNotFound`.
- Обработчик: `errors.Is` → 404, иначе 500.

**Файлы.**
```
~ internal/database/tasks.go      (GetByID, var ErrTaskNotFound)
~ cmd/api/main.go                 (роут GET /tasks/{id} + обработчик)
```

**Как проверить.**
```
curl -i localhost:8080/tasks/1     → 200 + объект
curl -i localhost:8080/tasks/9999  → 404
curl -i localhost:8080/tasks/abc   → 400
```

### 🟡 Шаг 7. POST /tasks

**Что это и зачем.**
Создание записи. Клиент шлёт JSON в теле запроса, сервер его *десериализует*
(парсит в структуру), валидирует и сохраняет. Здесь появляется разделение
«что приходит на вход» и «что хранится»: на вход — отдельная структура.

**Что реализуем.**
- `CreateTaskInput` в `models` — только поля, которые клиент может задать при
  создании (без `id`, `created_at` — их ставит сервер/БД).
- `json.NewDecoder(r.Body).Decode(&input)`; ошибка парсинга → `400`.
- Валидация (например, `title` не пустой → иначе `400`).
- `TaskStore.Create(input)` — `INSERT ... RETURNING ...`, вернуть созданную задачу.
- Ответ `201 Created` с телом созданной задачи.

**Почему отдельная input-структура.**
Если принимать прямо `Task`, клиент сможет прислать свой `id` или `created_at`
и сломать инварианты. Input-DTO задаёт **контракт входа** — что именно разрешено.

**Файлы.**
```
~ internal/models/task.go         (CreateTaskInput)
~ internal/database/tasks.go      (Create)
~ cmd/api/main.go                 (роут POST /tasks + обработчик)
```

**Как проверить.**
```
curl -i -X POST localhost:8080/tasks -d '{"title":"new"}'   → 201 + объект с id
curl -i -X POST localhost:8080/tasks -d '{"title":""}'      → 400
curl -i -X POST localhost:8080/tasks -d 'not json'          → 400
```

### 🟡 Шаг 8. PUT /tasks/{id}

**Что это и зачем.**
Обновление записи. Тонкий момент: клиент может захотеть поменять **только одно
поле** (например, отметить выполненной), не трогая остальные. Как отличить
«поле не прислали» от «прислали пустое значение»?

**Какие бывают подходы к обновлению.**
- **PUT (полная замена)** — клиент присылает объект целиком, сервер заменяет все
  поля. Просто, но клиент обязан прислать всё, иначе затрёт данные пустотой.
  *Где используется:* простые API, где запись всегда редактируется целиком.
- **PATCH (частичное обновление)** — клиент шлёт только изменяемые поля.
  *Где используется:* большинство современных API, мобильные клиенты («тоггл
  чекбокса» шлёт одно поле).

**Приём в Go для частичного обновления — указатели.**
В `UpdateTaskInput` поля делаются указателями: `*string`, `*bool`. `nil` =
«поле не прислали, не менять»; не-`nil` = «прислали, применить (даже если это
пустая строка/false)». Так различается «отсутствие» и «пустое значение».

**Что реализуем.**
- `UpdateTaskInput` с полями-указателями.
- `TaskStore.Update(id, input)` через **read-modify-write**: прочитать запись,
  применить только не-`nil` поля, записать.
- Несуществующий id → 404 (тот же `ErrTaskNotFound`).

**Файлы.**
```
~ internal/models/task.go         (UpdateTaskInput)
~ internal/database/tasks.go      (Update)
~ cmd/api/main.go                 (роут PUT /tasks/{id} + обработчик)
```

**Как проверить.**
```
curl -X PUT localhost:8080/tasks/1 -d '{"completed":true}'  → только completed изменился
curl -i -X PUT localhost:8080/tasks/9999 -d '{"title":"x"}' → 404
```

### 🟡 Шаг 9. DELETE /tasks/{id}

**Что это и зачем.**
Удаление записи. Простой эндпоинт, но снова всплывает вопрос «а если такой
записи нет».

**Какие бывают подходы к удалению.**
- **Hard delete** — физически удалить строку (`DELETE FROM ...`). Просто.
- **Soft delete** — пометить `deleted_at = now()`, а в выборках фильтровать
  `WHERE deleted_at IS NULL`. *Где используется:* там, где нужна история/восстановление
  (биллинг, аккаунты пользователей). Дороже: каждую выборку надо помнить фильтровать.

Берём **hard delete** — для учебного CRUD достаточно.

**Что реализуем.**
- `TaskStore.Delete(id)` — `DELETE ... WHERE id = $1`.
- Проверить `RowsAffected()`: если 0 — записи не было → `ErrTaskNotFound` → 404.
- Успех — `204 No Content` (тело не нужно).

**Файлы.**
```
~ internal/database/tasks.go      (Delete)
~ cmd/api/main.go                 (роут DELETE /tasks/{id} + обработчик)
```

**Как проверить.**
```
curl -i -X DELETE localhost:8080/tasks/1     → 204
curl -i -X DELETE localhost:8080/tasks/1     → 404 (уже удалена)
```

### 🟢 Шаг 10. Слои и хелперы

**Что это и зачем.**
К этому моменту все обработчики свалены в `main.go`, и в коде накопились
повторения (выставление заголовков, кодирование JSON, формат ошибок). Пора
навести **слоистую архитектуру** — это главный продакшен-навык из всего проекта.

**Принцип — однонаправленная зависимость.**
```
handlers → database → models
```
- **handlers** знают про HTTP (запрос, ответ, статусы), не знают про SQL.
- **database** знает про SQL, не знает про HTTP.
- **models** — простые структуры данных, не знают ни про то, ни про другое.

Зачем: каждый слой можно менять и тестировать отдельно; если завтра тот же стор
понадобится в CLI-утилите — он переиспользуется без переписывания.

**Что реализуем.**
- Создать `internal/handlers`: `Handler`-структура, которая держит `*TaskStore`.
- **Перенести** все обработчики из `main.go` в этот пакет.
- Хелперы `respondWithJSON(w, status, payload)` и `respondWithError(w, status, msg)` —
  убрать дублирование. Единый формат ошибки: `{"error":"..."}`.
- `main.go` худеет: только чтение env, сборка зависимостей (store → handler) и
  регистрация маршрутов.

**Файлы.**
```
+ internal/handlers/handlers.go   (Handler, обработчики, respondWithJSON/Error)
~ cmd/api/main.go                 (обработчики уезжают; остаётся сборка + роутинг)
```

**Как проверить.**
- Поведение не меняется (те же ответы), но код стал чище: ошибки везде в одном
  формате, заголовки выставляются в одном месте.

### 🟢 Шаг 11. DTO-разделение

**Что это и зачем.**
DTO (Data Transfer Object) — структура «для передачи», в отличие от модели
хранения. Часто **ответ списка** не должен содержать все поля: например, в
списке задач не нужны тяжёлые или лишние поля, которые есть в детальном ответе.

**Что реализуем.**
- `Task` — полная сущность (детальный ответ `GET /tasks/{id}`).
- `TaskListItem` — урезанная проекция для списка (`GetAll`), только нужные поля.
- `GetAll` теперь возвращает `[]TaskListItem`.

**Зачем разделять.**
Контракт ответа становится явным и управляемым: меняешь детальный ответ — не
ломаешь список, и наоборот.

**Файлы.**
```
~ internal/models/task.go         (TaskListItem)
~ internal/database/tasks.go      (GetAll → []TaskListItem)
```

**Как проверить.**
```
curl localhost:8080/tasks      → элементы с урезанным набором полей
curl localhost:8080/tasks/1    → полный объект
```

### 🟢 Шаг 12. Logging middleware

**Что это и зачем.**
Middleware («промежуточный слой») — это обёртка вокруг обработчика, которая
выполняет что-то **до и после** него для *всех* запросов сразу. Логирование —
классический пример: на каждый запрос записать метод, путь и время выполнения.

**Паттерн.**
Middleware — функция, принимающая `http.Handler` и возвращающая новый
`http.Handler`, который внутри вызывает исходный, добавляя поведение вокруг.
Так оборачивают весь роутер один раз, и логируются все эндпоинты.

**Что реализуем.**
- `loggingMiddleware(next http.Handler) http.Handler` — засекает время, вызывает
  `next`, логирует `метод путь длительность`.
- Обернуть им `ServeMux` в `main.go`.

**Где ещё применяется паттерн.**
Тот же приём — для аутентификации, CORS, восстановления после паники (recover),
ограничения частоты запросов (rate limit). Middleware — фундаментальный кирпич
HTTP-сервера.

**Файлы.**
```
+ internal/handlers/middleware.go   (loggingMiddleware)
~ cmd/api/main.go                   (оборачивает роутер middleware)
```

**Как проверить.**
- Любой запрос печатает в лог строку вида `GET /tasks 200 1.3ms`.

## Фаза B — листинг

> Превращаем `GET /tasks` из «отдать всё» в зрелый list-эндпоинт:
> поиск → пагинация → фильтры → сортировка. Все они комбинируются через
> один и тот же набор query-параметров и один билдер `WHERE`.
>
> Файлы этой фазы повторяются: параметры запроса копятся в `internal/models`,
> построение SQL — в `internal/database/tasks.go`, парсинг query — в
> `internal/handlers`. Новых пакетов не добавляется.

### 🟢 Шаг 13. Поиск

**Что это и зачем.**
Поиск — отдать только записи, где текстовое поле содержит подстроку. Клиент шлёт
`?search=...`, сервер ищет совпадения в `title`/`description`.

**Какие бывают (лесенка поиска в Postgres).**
- **`LIKE` / `ILIKE`** — поиск подстроки. `ILIKE` = регистронезависимый.
  Просто, но без индекса медленно на больших таблицах. *Где используется:*
  небольшие таблицы, простой поиск «содержит».
- **Полнотекстовый поиск (FTS, `tsvector`/`tsquery` + GIN-индекс)** — умеет
  словоформы, стоп-слова, ранжирование. *Где используется:* поиск по статьям,
  описаниям, где важны словоформы («бегать» находит «бежал»).
- **`pg_trgm`** — индекс для быстрого `ILIKE`-поиска подстроки. *Где
  используется:* автодополнение, «похожие строки».
- **Внешние движки (Elasticsearch, Meilisearch)** — когда поиск становится
  отдельной большой задачей.

Берём **`ILIKE`** — корректно работает сразу; быстродействие оптимизируем
позже (индексами), когда понадобится. Правило «сначала корректно, потом быстро».

**Что реализуем.**
- `?search=...` → условие `title ILIKE $1 OR description ILIKE $1` (со скобками!).
- Значение оборачивается в `%...%` (это делает слой database, не handler).
- Если `search` пустой — условие не добавляется вообще.
- **Единый билдер `WHERE`**: завести функцию, которая из параметров собирает
  фрагмент `WHERE` и список аргументов. Она понадобится и для подсчёта `total`.

**Подводные камни.**
- Символы `%` и `_` в запросе пользователя — это спецсимволы LIKE. Для честного
  поиска подстроки их экранируют (на учебном этапе можно отложить, пометив TODO).
- `NULL`-поля: `NULL ILIKE '...'` → не совпадает. Если поле может быть `NULL` —
  оборачивать `COALESCE(col, '')`.

**Файлы.**
```
~ internal/models/task.go         (структура параметров листинга: Search)
~ internal/database/tasks.go      (buildTasksWhere, GetAll использует WHERE)
~ internal/handlers/handlers.go   (парсинг ?search)
```

**Где какой слой.**
- handlers — достать `search` из query, обрезать пробелы, отдать в стор сырым.
- database — собрать `WHERE`, обернуть в `%...%`, подставить через `$N`.

**Как проверить.**
```
curl 'localhost:8080/tasks?search=first'   → только совпадения
curl 'localhost:8080/tasks?search='        → все задачи (поиск не применяется)
```

### 🟢 Шаг 14. Пагинация

**Что это и зачем.**
Пагинация — отдача списка не целиком, а кусками («страницами»). Без неё на
большой таблице сервер сожрёт память, сеть передаст мегабайты, клиент повиснет.
Клиент просит «дай кусок»: например, 20 записей с определённого места.

**Какие бывают (две стратегии).**

**1. Offset / Limit** — «пропусти N, отдай M» (`?limit=20&offset=40`).
- *Плюсы:* просто, можно прыгнуть на любую страницу (`offset=(page-1)*limit`),
  легко показать «страница 3 из 50».
- *Минусы:* на больших таблицах медленно (БД проходит первые `offset` строк,
  чтобы пропустить); при вставке/удалении между запросами страницы «съезжают»
  (дубль или пропуск записи).
- *Где используется:* админки, таблицы с номерами страниц, GitHub (`?page=`),
  поисковая выдача с пронумерованными страницами.

**2. Cursor / Keyset** — «дай записи после вот этой» (`?limit=20&after=<курсор>`).
- *Плюсы:* быстро на любой глубине (использует индекс, не считает offset), не
  «съезжает» при вставках.
- *Минусы:* нельзя прыгнуть на «страницу 17», только «следующая/предыдущая»;
  курсор надо кодировать (обычно `created_at`+`id` последней записи в base64).
- *Где используется:* **ленты соцсетей и бесконечный скролл** (Twitter/X,
  Instagram, Slack-история сообщений), API с большими и часто меняющимися
  данными (Stripe использует курсоры), мобильные «подгрузить ещё».

**Правило выбора:** нужны номера страниц и прыжки — offset; бесконечная лента и
большие/живые данные — cursor. Берём **offset/limit**: проще, нагляднее, и ты
прямо увидишь его слабые места — после этого осознанно поймёшь, *зачем* курсорная.

**Что реализуем.**
- `?limit=` и `?offset=` из query.
- **Дефолт** `limit=10`, если не передан (иначе клиент случайно вытащит всё).
- **Максимум** `limit=100` (защита сервера); больше — обрезать или `400`.
- **Валидация**: не число / отрицательное → `400`, не молчаливый 0.
- **Форма ответа** — данные и метаданные раздельно:
  ```json
  {
    "data": [ { "id": 1, "title": "..." } ],
    "meta": { "limit": 10, "offset": 40, "total": 125 }
  }
  ```
  `total` — **общее** число подходящих записей (для расчёта числа страниц), а не
  размер текущего куска.
- `total` — отдельным запросом `SELECT COUNT(*)` с **тем же** `WHERE`, что и
  основная выборка (иначе соврёт). Тут и пригождается единый билдер из шага 13.
- **Стабильный порядок**: `ORDER BY created_at DESC, id DESC`. Без тай-брейкера
  по `id` записи с одинаковым `created_at` идут в случайном порядке — при
  пагинации появляются дубли/пропуски.

**Файлы.**
```
~ internal/models/task.go         (Limit, Offset, Total; структура ответа data+meta)
~ internal/database/tasks.go      (LIMIT/OFFSET, отдельный COUNT)
~ internal/handlers/handlers.go   (парсинг + валидация limit/offset)
```

**Где какой слой.**
- handlers — парсят `limit`/`offset`, валидируют, дефолтят, отдают `400`.
- database — подставляют `LIMIT $N OFFSET $N`, делают `COUNT`.
- models — структура ответа с `data` и `meta { limit, offset, total }`.

**Как проверить.**
```
curl 'localhost:8080/tasks?limit=2&offset=0'   → первые 2, total = общее
curl 'localhost:8080/tasks?limit=2&offset=2'   → следующие 2, total тот же
curl 'localhost:8080/tasks?limit=0'            → 400
curl 'localhost:8080/tasks?limit=abc'          → 400
curl 'localhost:8080/tasks?offset=-1'          → 400
```

### 🟡 Шаг 15. Фильтры

**Что это и зачем.**
Фильтр — отдать только записи, удовлетворяющие условию по конкретному полю:
«только выполненные», «созданные после такой-то даты». В отличие от поиска (по
тексту) — это точные условия по типизированным полям.

**Какие бывают фильтры.**
- **Точное равенство:** `?completed=true`.
- **Диапазон:** `?created_after=<дата>&created_before=<дата>`.
- **Множество (IN):** `?id=1,2,3`.
- **Наличие/отсутствие:** `?has_description=true`.

**Стили записи в URL.**
- **Плоский:** `?completed=true&created_after=...`. Просто, curl-дружелюбно.
  *Где используется:* GitHub, большинство простых API.
- **Operator-suffix:** `?created_at[gte]=...`. Систематично, но скобки в URL
  неудобны. *Где используется:* JSON:API, Strapi.

Берём **плоский** стиль. Конкретно реализуем `?completed=true|false` и
`?created_after=<RFC3339>`.

**Что реализуем.**
- Расширить **тот же** `buildTasksWhere` новыми условиями (одно место → `GetAll`
  и `COUNT` автоматически согласованы).
- Опциональные поля в параметрах — через **указатели** (`*bool`, `*time.Time`):
  `nil` = «фильтр не задан, в `WHERE` не идёт». (Тот же приём, что в `UpdateTaskInput`.)
- Несколько фильтров одновременно комбинируются через `AND`.

**Подводные камни.**
- Парсинг типов строго: булево — только `true`/`false`; дата — только RFC3339.
  Мусор → `400`, не молчаливое игнорирование.
- Скобки вокруг `OR`-условия поиска обязательны, иначе `AND` фильтра привяжется
  не туда (приоритет операторов).

**Файлы.**
```
~ internal/models/task.go         (Completed *bool, CreatedAfter *time.Time)
~ internal/database/tasks.go      (новые условия в buildTasksWhere)
~ internal/handlers/handlers.go   (парсинг ?completed, ?created_after)
```

**Где какой слой.**
- handlers — распарсить `completed`/`created_after`, провалидировать типы.
- database — добавить условия в общий билдер `WHERE`.

**Как проверить.**
```
curl 'localhost:8080/tasks?completed=true'                  → только выполненные
curl 'localhost:8080/tasks?created_after=2026-01-01T00:00:00Z'
curl 'localhost:8080/tasks?completed=maybe'                 → 400
```

### 🟡 Шаг 16. Сортировка

**Что это и зачем.**
Сортировка — отдать список в заданном порядке: по дате, по названию, по статусу.
Клиент указывает, по какому полю и в какую сторону.

**Какие бывают форматы записи в URL.**
- **Минус-префикс (JSON:API):** `?sort=-created_at` (минус = по убыванию).
  Лаконично. *Где используется:* JSON:API, Ember.
- **Поле:направление:** `?sort=created_at:desc,title:asc`. Явно и читаемо.
  *Где используется:* многие REST API, когда нужна явность.

Берём **`field:direction`** через запятую для мульти-сортировки.

**Главное отличие от всего предыдущего — безопасность.**
Значения подставляются через `$N` (параметры). А **имя колонки** через `$N`
подставить нельзя — Postgres так не умеет. Имя приходится вставлять
**конкатенацией строки**. Если брать его напрямую из запроса пользователя — это
**SQL-инъекция** (`?sort=title;DROP TABLE tasks`). Поэтому имя колонки берётся
**только из заранее зафиксированного whitelist**.

**Что реализуем.**
- Распарсить `?sort=field:dir,field:dir` в `[]SortRule{ Field, Desc }`.
- **Whitelist** разрешённых колонок (`created_at`, `updated_at`, `completed`,
  `title`) и направлений (`asc`/`desc`). Не из списка → `400`.
- Построить `ORDER BY` конкатенацией имён из whitelist.
- Дефолт сортировки, если не передана: `created_at DESC`.
- **Тай-брейкер**: в конец всегда добавлять `id DESC` для стабильности (см. шаг 14).

**Файлы.**
```
~ internal/models/task.go         (тип SortRule)
~ internal/database/tasks.go      (сборка ORDER BY из правил + тай-брейкер)
~ internal/handlers/handlers.go   (парсинг ?sort, проверка по whitelist)
```

**Где какой слой.**
- handlers — распарсить `sort`, проверить по whitelist, отдать `[]SortRule`.
- database — собрать `ORDER BY` из правил + тай-брейкер.

**Как проверить.**
```
curl 'localhost:8080/tasks?sort=title:asc'
curl 'localhost:8080/tasks?sort=completed:desc,created_at:asc'
curl 'localhost:8080/tasks?sort=secret_col:asc'   → 400 (нет в whitelist)
```

## Фаза C — новые сущности

> Чтобы добавлять и менять таблицы без потери данных, сначала ставим инструмент
> миграций, затем на его основе вводим связанную сущность (проекты).

### 🟠 Шаг 17. Инструмент миграций (`goose`)

**Что это и зачем.**
Пока схема живёт в `sql/init.sql`, который выполняется **один раз** при создании
БД. Любое изменение схемы = пересоздание базы с потерей данных. В реальной
разработке схема **эволюционирует** многократно, и данные терять нельзя. Решение —
**миграции**: пронумерованные SQL-файлы с командами «накатить» (Up) и «откатить»
(Down), плюс инструмент, который помнит, какие уже применены.

**Какие бывают инструменты (для Go).**
- **`goose`** — простой, файлы `.sql` с секциями `+goose Up` / `+goose Down`.
  *Где используется:* небольшие и средние проекты, быстрый старт.
- **`golang-migrate`** — индустриальный стандарт, поддержка многих БД.
- **`atlas`** — декларативный (описываешь желаемую схему, инструмент сам считает
  разницу). Современный, но сложнее на старте.

Берём **`goose`** — минимальный порог входа.

**Что реализуем.**
- Установить `goose`.
- Перенести содержимое `init.sql` в первую миграцию `0001_init.sql` (Up — создать
  таблицу + сиды; Down — удалить таблицу).
- Убрать монтирование `init.sql` из docker-compose (теперь схему накатывает goose).
- Команду `goose up` задокументировать в README / Makefile.

**Новый рабочий процесс смены схемы.**
```
goose create add_column sql   → новый файл миграции
# пишешь Up/Down
goose up                       → применяет новые миграции, данные сохраняются
goose down                     → откатывает последнюю
```

**Файлы.**
```
+ migrations/0001_init.sql        (схема + сиды, перенесены из init.sql)
+ Makefile                        (цели migrate-up / migrate-down) — опционально
~ docker-compose.yml              (убрать монтирование init.sql)
- sql/init.sql                    (удаляется, заменён миграцией)
```

**Как проверить.**
```
goose status   → список применённых/ожидающих миграций
# после goose up таблица и сиды на месте, данные при повторном up не теряются
```

### 🟠 Шаг 18. Проекты (project содержит задачи)

**Что это и зачем.**
До сих пор была одна таблица. Реальные домены — это **связанные** сущности.
Вводим `projects`: проект содержит задачи (один-ко-многим). Это знакомство с
внешними ключами (FK), связями и вложенными ресурсами в REST.

**Что такое связь один-ко-многим и FK.**
У задачи появляется колонка `project_id`, ссылающаяся на `projects.id` (внешний
ключ). FK гарантирует целостность: нельзя сослаться на несуществующий проект.
Надо решить: задача обязана принадлежать проекту (`NOT NULL`) или может быть «без
проекта» (`NULL`); что делать с задачами при удалении проекта (запретить /
каскадно удалить / обнулить).

**Какие бывают способы отдать связанные данные в REST.**
- **Вложенный ресурс:** `GET /projects/{id}/tasks` — «задачи этого проекта».
  *Где используется:* когда связь — часть иерархии URL.
- **Фильтр на основном ресурсе:** `GET /tasks?project_id=5`. *Где используется:*
  когда задачи — самостоятельный ресурс, проект — лишь один из фильтров.

Можно сделать **оба** — они не противоречат друг другу.

**Что реализуем.**
- Миграция `0002_add_projects.sql`: таблица `projects` + колонка `tasks.project_id`
  с FK.
- Модель `Project`, `ProjectStore`, CRUD-эндпоинты `GET/POST /projects`,
  `GET/PUT/DELETE /projects/{id}` (повторяешь пройденный паттерн на новой сущности —
  закрепление).
- Связь: `GET /projects/{id}/tasks` и/или фильтр `?project_id=` в листинге задач.

**Что понять про JOIN.**
Если в ответе задачи нужно показать имя проекта (а не только `project_id`) — это
`JOIN` таблиц в запросе. Первый шаг от «одна таблица» к «реляционным» запросам.

**Файлы.**
```
+ migrations/0002_add_projects.sql    (таблица projects + FK tasks.project_id)
+ internal/models/project.go          (Project + DTO)
+ internal/database/projects.go       (ProjectStore)
+ internal/handlers/projects.go       (обработчики проектов)
~ internal/database/tasks.go          (фильтр project_id / JOIN при необходимости)
~ cmd/api/main.go                     (роуты /projects, /projects/{id}/tasks)
```

**Как проверить.**
```
curl -X POST localhost:8080/projects -d '{"name":"Work"}'
curl localhost:8080/projects/1/tasks
curl 'localhost:8080/tasks?project_id=1'
```

## Фаза D — продакшен-полировка

### 🟢 Шаг 19. Структурное логирование + healthcheck

**Что это и зачем.**
Простой `log.Printf` пишет строки, которые человек читает глазами.
**Структурное логирование** пишет логи как набор полей (ключ-значение), которые
машина может фильтровать и искать — это нужно, когда логов много и их собирает
система мониторинга. В Go для этого есть стандартный `log/slog`.
**Healthcheck** — эндпоинт, по которому оркестратор (Docker, Kubernetes) проверяет,
жив ли сервис и готов ли принимать трафик.

**Что реализуем.**
- Перевести логирование на `log/slog` со структурными полями
  (`method`, `path`, `status`, `latency_ms`, при наличии — `request_id`).
- `GET /health` — **liveness**: приложение запущено (отдаёт 200 без проверок).
- `GET /ready` — **readiness**: зависимости доступны (пингует БД; если БД лежит —
  503). Разница: liveness — «процесс жив», readiness — «готов обслуживать».

**Где используется.**
Healthcheck-эндпоинты — стандарт для деплоя в контейнерах: по ним балансировщик
решает, слать ли трафик на инстанс, а оркестратор — перезапускать ли упавший.

**Файлы.**
```
+ internal/handlers/health.go     (обработчики /health и /ready)
~ internal/handlers/middleware.go (логирование переходит на slog)
~ cmd/api/main.go                 (настройка slog, роуты /health и /ready)
```

**Как проверить.**
```
curl localhost:8080/health    → 200
curl localhost:8080/ready     → 200, а при остановленной БД → 503
# в логах — строки с полями, а не свободный текст
```
